Encryption and sync

Key model

  • Master key: 32 random bytes generated on the client and shown as a recovery key (Crockford base32 in groups of four, with a 2-byte checksum to catch typos). It never leaves the device.
  • Derived values (HKDF-SHA-256, salt centime/v1): a public user id, an auth secret and an AES-256-GCM key.
  • Sealed blobs: random 12-byte IV, format version byte, user id bound as additional authenticated data.
  • Authentication: Authorization: Bearer <userId>.<secret>. The server stores only the SHA-256 of the secret and compares in constant time. No password, no session.

Pairing another device with a QR code

Typing the recovery key on a phone is painful, so an already configured device can hand it over.

  1. On the web or desktop app, open Settings › Encryption key and click Show QR code. It encodes a centime://link?v=1&k=<key>&s=<server> URI: the recovery key and the server address, if one is configured.
  2. On the Android app's first launch, choose Scan a QR code and point the camera at it.
  3. The key and the server are saved on the phone, which then syncs like any other device.

The QR code carries the key in clear text: anyone who photographs it can read your data. Hide it again once the phone is paired.

Synchronization

The server is a dumb, ordered, append-only log. Clients do the merging.

  1. Pull: read the log from the stored cursor, decrypt each entry and apply its rows.
  2. Push: send local rows not yet synced, in sealed batches.
  3. Conflicts: the most recent updatedAt wins. For duplicates created offline on two devices, the smallest id wins everywhere and the loser is aliased.
  4. An entry that fails to decrypt aborts the sync: wrong key, or tampered data.

Sync runs at startup, every 5 minutes, 5 seconds after each change, and on demand from the sidebar.

Receipt images

Receipt images are sealed with the same AES-256-GCM key as the database and the log, in the same self-contained format. After each log sync, the device uploads the sealed bytes as they are to /api/blob/<receipt id>, and the other devices download them unchanged. The relay sees only ciphertext, its size and the receipt id; the file type and the fingerprint stay in the encrypted log.

The AI reading exception

Your data never leaves your devices unencrypted, with one opt-in exception. If you turn on Settings › AI receipt reading, each receipt photo read by the AI is sent in clear over HTTPS, with the names of your categories, from your device to Anthropic's API. The relay is not involved. The option is off by default, uses your own API key stored only in the encrypted local database, and sends nothing while it is off. See Receipts.

Threat model in short

A compromised or curious server sees ciphertext, sizes and timing, not your transactions. A stolen device or application folder exposes the key and data on it, hence the advice to use disk encryption.
